# 05｜代理工程整合評估：EGM × Claude Code × Imagine × Jev

本文件提出**研究建議**，不是安裝指令、現有設定事實或執行授權。

## 1. 各元件真正處理不同問題

| 問題 | 優先技術 | 為什麼 |
| --- | --- | --- |
| 需求模糊、規格互相矛盾 | EGM Draft + Review | 提前查找規格缺漏與錯誤假設 |
| 主代理上下文被搜尋資訊塞滿 | Haiku 子代理 | 把搜尋結果留在子上下文，回傳摘要和證據 |
| 重大工程判斷需要第二意見 | Opus Advisor | 同步主對話背景、提供高階建議 |
| 最終程式與核准規格偏離 | EGM Drift Report + 測試 | 比對意圖與實作，CI 再確認行為 |
| 對話需要圖表與 UI 原型 | Imagine 設計原則 / 視覺化 | 改善人類理解與討論品質 |
| 大量小決策需要模型路由 | Jev + 確定性規則 | 低成本分類與升級策略的候選方案 |

## 2. 推薦實驗順序

### 第一階段：只做文檔與查證

- 使用 EGM 的規格模板，記錄已確認需求、未確認假設、來源和驗收條件。
- 引用 Imagine 的設計原則編排結論，不導入插件與新 runtime。
- 為同一任務測試「原始開發流程」與「先寫規格流程」的品質。

### 第二階段：獨立測試環境比較多模型

- 選定三種規模的樣本：小 Bug、中等功能、跨模組改造。
- 先固定主模型，逐步新增唯讀搜索子代理、Advisor。
- 每個步驟都量測有效問題數／返工數／總 Token／延遲，排除純感覺的改善。
- 規範子代理權限與任務結果格式，需人工批准後才寫入其他專案。

### 第三階段：Jev shadow mode

- 只有在路由次數夠多時才測 Jev。
- Shadow 模式先看錯誤率和是否把敏感工作送錯模型。
- 沒有足夠證據，保持「不自動執行」。

## 3. Hermes / Codex 的特殊注意事項

先前工作規則：使用 `default` Profile、停用子代理、總並發上限 2、保留人工審批。

因此不能不經同意就把貼文中的「三個 Haiku 並行 + Opus 顧問」加入 Hermes；它也與原版 EGM Goldfish 需要真實隔離子代理的條件不同。

**結論：**
- 能先用的是規格文件標準、查證報告、設計原則；
- 要測完整 Goldfish，必須另行確認宿主提供真的 fresh-context subagent；
- 要測三模型分工，必須建立獨立實驗環境，明確限制並發、資源與權限；
- Jev 不是第一階段的必要依賴。

## 4. 成本／品質衡量指標

| 指標 | 定義 | 為什麼記 |
| --- | --- | --- |
| 通過率 | 完成相同驗收需求的比例 | 避免只看速度 |
| 返工量 | 修復首次產出缺陷所需的編輯／測試輪數 | 測量真正工程效率 |
| Token | 主代理 + 子代理 + Advisor + cache | 全部計入 |
| 費用 | 按模型實際計價與帳戶使用方式 | 檢驗省錢主張 |
| 耗時 | 從任務開始到驗收通過的總時間 | 避免只看個別回應 |
| 越權事件 | 未批准修改、讀取超過授權等 | 用來驗證治理 |
| 規格缺陷 | 重要未定義條件、衝突與缺失 | 衡量 EGM 價值 |

## 5. 風險守則

- 不讓任何低成本模型直接決定刪檔、部署、合併、讀取秘密、放寬權限。
- 不因為工具描述寫「唯讀」就假設安全；檢查實際工具白名單。
- Git worktree 不等於 OS sandbox，也不消除共用 secrets 的風險。
- 未經批准，不修改既有倉庫的 `AGENTS.md`、`CLAUDE.md`、hooks、CI 或使用者全域 Profile。
